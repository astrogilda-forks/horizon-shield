# hs-pilot

The responder side of [horizon-shield Issue #51](https://github.com/ogasurfproject-jpg/horizon-shield/issues/51): one metered call of HORIZON SHIELD's estimate audit, on a testnet, for the pilot proposed on aeoess/agent-governance-vocabulary#177.

- `GET /.well-known/pilot.json`: the responder key, the price and unit, the service name.
- `POST /call` with `{request, task, fixture, payment}`: checks that the task is this service at this price, that the request occurrence commits to the task and names this responder, that the payment is payer-signed by the request's caller, to this responder, for this request, at the task's price; audits every line of the fixture through the public MCP server's `audit_estimate`; returns the audit and a `musubi.ca2a.execution-receipt.v0` signed with the responder key, naming the block the worker had just seen. The audit names its input by digest (`fixture_sha256`) and is a function of the inputs and of the dataset version (each line carries `dataset_sha256` and the ruleset), so the acceptance criteria of #51 can check it by hash equality: the audit of a different fixture fails the first criterion, it is not left unevaluated. Each line carries the quoted amount, the matched work, the fair range, the reference amount (quantity times the range's average), and a finding `within`, `above`, `below` or `unmatched`; the audit carries the quote total and the reference total (null when any line is unmatched). No region multiplier is applied unless the call names a region.

- `POST /void` with `{request, void}`, where `void` is a `musubi.ca2a.void-request.v0` `{type, caller, request_sha256, signature}` signed by the request's caller: the answer to a lost call. If the worker has already signed a receipt for that occurrence, it returns that receipt and audit (`status: executed`) and voids nothing. Otherwise it signs and stores a `musubi.ca2a.non-execution.v0` statement `{type, responder, caller, lineage, capability, request_sha256, seen_block, outcome: {kind: not_executed}, void_request_sha256, signature}`: this responder has issued no execution receipt for that occurrence as of `seen_block`, and will issue none; every later `/call` for it is refused `request_voided` (`status: not_executed`). Asking again returns the same stored statement. Only the caller can void, so no third party can block an occurrence it does not own.

It logs nothing (the caller logs the use, the payment and the receipt with the log operator), settles no rail (the payment receipt is checked for shape and binding and carried by digest) and decides no budget (`pilot_v0.py` does, afterwards). Its only state is one KV namespace (`STATE`) holding, per request occurrence, the receipt it signed or the non-execution statement, so that each occurrence is answered once: a repeated `/call` for an executed occurrence returns the stored receipt and audit with `replay: true`, without auditing or signing again. KV is eventually consistent across locations (up to about a minute), so a caller sends `/void` or `/call` for an occurrence, never both at once. Without the binding the worker keeps no state and refuses `/void` with `no_state`.

`node --test test/pilot.test.mjs` runs it against a mocked MCP server and block source. A receipt it signs parses and verifies under `musubi-v0/ca2a-companion-v0/companion_v0.py`, and its RFC 8785 bytes equal the Python reference's.

Deploy: `wrangler kv namespace create hs-pilot-state` and put its id in `wrangler.jsonc` (the id is not a secret), `wrangler secret put RESPONDER_SEED` (64 hex, a fresh Ed25519 seed, kept in the key manager; already set for the #51 key), then `wrangler deploy`. Post the key from `/.well-known/pilot.json` in #51.
