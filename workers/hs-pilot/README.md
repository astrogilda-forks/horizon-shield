# hs-pilot

The responder side of [horizon-shield Issue #51](https://github.com/ogasurfproject-jpg/horizon-shield/issues/51): one metered call of HORIZON SHIELD's estimate audit, on a testnet, for the pilot proposed on aeoess/agent-governance-vocabulary#177.

- `GET /.well-known/pilot.json`: the responder key, the price and unit, the service name.
- `POST /call` with `{request, task, fixture, payment}`: checks that the task is this service at this price, that the request occurrence commits to the task and names this responder, that the payment is payer-signed by the request's caller, to this responder, for this request, at the task's price; audits every line of the fixture through the public MCP server's `audit_estimate`; returns the audit and a `musubi.ca2a.execution-receipt.v0` signed with the responder key, naming the block the worker had just seen. The audit names its input by digest (`fixture_sha256`) and is a function of the inputs and of the dataset version (each line carries `dataset_sha256` and the ruleset), so the acceptance criteria of #51 can check it by hash equality: the audit of a different fixture fails the first criterion, it is not left unevaluated. Each line carries the quoted amount, the matched work, the fair range, the reference amount (quantity times the range's average), and a finding `within`, `above`, `below` or `unmatched`; the audit carries the quote total and the reference total (null when any line is unmatched). No region multiplier is applied unless the call names a region.

- `POST /void` with `{request, void}`, where `void` is a `musubi.ca2a.void-request.v0` `{type, caller, request_sha256, signature}` signed by the request's caller: the answer to a lost call. If the worker has already signed a receipt for that occurrence, it returns that receipt and audit (`status: executed`) and voids nothing. Otherwise it signs and stores a `musubi.ca2a.non-execution.v0` statement `{type, responder, caller, lineage, capability, request_sha256, seen_block, outcome: {kind: not_executed}, void_request_sha256, signature}`: this responder has issued no execution receipt for that occurrence as of `seen_block`, and will issue none; every later `/call` for it is refused `request_voided` (`status: not_executed`). Asking again returns the same stored statement. While a `/call` for that occurrence is still running, it answers `{status: in_progress, request_sha256, retry_after_s}` instead: unsigned, committing to nothing, voiding nothing; ask again after `retry_after_s` seconds. Only the caller can void, so no third party can block an occurrence it does not own.

It logs nothing (the caller logs the use, the payment and the receipt with the log operator), settles no rail (the payment receipt is checked for shape and binding and carried by digest) and decides no budget (`pilot_v0.py` does, afterwards). Its state is one KV namespace (`STATE`) holding, per request occurrence, the receipt it signed or the non-execution statement, and, with the `OCCURRENCE` binding, one Durable Object per occurrence (below), so that each occurrence is answered once: a repeated `/call` for an executed occurrence returns the stored receipt and audit with `replay: true`, without auditing or signing again. Without `STATE` the worker keeps no state and refuses `/void` with `no_state`.

## The race between /call and /void (fixed 2026-10-21)

Reported by aeoess on #51: `/call` checked for a void and a receipt before the audit and never again, and `/void` checked only for a receipt. A `/void` that arrived while a `/call` was still auditing therefore signed `not_executed`, and the call then finished and signed a receipt for the same occurrence. Two layers now close it.

1. In the handlers, on any store. A `/call` writes an in-flight marker (`run:<request_sha256>`, with a run id and its start time, KV `expirationTtl` 120 s) before the audit. Right before signing it checks again: that it is less than 25 s since it started, that no void exists, that no receipt exists, and that the marker is still its own. If any of these fails it refuses (`call_expired`, `request_voided`, `in_progress`) and signs nothing. It removes its marker only after its receipt is stored, or when it signed nothing. A `/void` reads the marker, then the receipt, then the stored void, and signs `not_executed` only when there is no receipt and no live marker. A second `/call` while one is running is refused `in_progress`. A marker older than 60 s is from a call that can no longer sign (it would refuse `call_expired` at its check), so it stops blocking: a crashed call delays a void by at most a minute, and can never produce a receipt afterwards.
2. Atomicity, with the `OCCURRENCE` binding. The worker checks the request occurrence, computes `request_sha256`, and forwards `/call` and `/void` to a SQLite-backed Durable Object (class `Occurrence`) named by that digest. The object runs them one at a time under `blockConcurrencyWhile`, from the first read to the last write, audit included, and its own transactional storage is the authority for the receipt, the void and the marker. A `/void` sent during a `/call` for the same occurrence waits for it and answers `executed` with that call's receipt. When the object holds nothing for an occurrence it reads `STATE`, so answers recorded before this change (the receipts of the earlier run, `hs51-musubi-A`, `-B`, `-C`) are still served as replays and as `executed`. Receipts and statements are written to `STATE` first and then to the object, so KV readers keep working and a write cut half way is still seen. A body whose request does not check is refused in the worker itself, with no state touched, exactly as before.

What `not_executed` now guarantees: it is final. Once this responder has signed a non-execution statement for an occurrence, no execution receipt for that occurrence will ever follow it, from a call that was already running or from any later one. With the `OCCURRENCE` binding this holds strictly, because the statement is signed only inside the object, when no call for the occurrence is running and none has stored a receipt, and every call checks for it inside the same object before signing. Without the binding it holds as far as KV is consistent: two locations that do not yet see each other's writes (up to about a minute) can still race.

`node --test test/pilot.test.mjs` (or `npm test`) runs it against a mocked MCP server and block source, including the reported interleaving with a delayed audit, stale and expired markers, the earlier run's KV receipts, and the Durable Object under a fake state whose `blockConcurrencyWhile` serializes strictly. A receipt it signs parses and verifies under `musubi-v0/ca2a-companion-v0/companion_v0.py`, and its RFC 8785 bytes equal the Python reference's.

Deploy: `wrangler kv namespace create hs-pilot-state` and put its id in `wrangler.jsonc` (the id is not a secret), `wrangler secret put RESPONDER_SEED` (64 hex, a fresh Ed25519 seed, kept in the key manager; already set for the #51 key), then `wrangler deploy` (the first deploy with the `OCCURRENCE` binding applies the `v1` migration that creates the `Occurrence` class; SQLite-backed Durable Objects run on the free plan). Post the key from `/.well-known/pilot.json` in #51.
